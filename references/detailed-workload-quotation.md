# 分部分项工作量统计与报价

## 适用条件

当任务同时具备以下任一特征时使用详细报价模式：

- 用户给出建设要求、招标清单或“分部分项工程清单与计价表”作为模板；
- 需要把现有系统能力与新增建设内容融合后逐功能估算；
- 需要按模块、功能、人员、阶段同时统计人日和金额；
- 最终成果需要 Excel、A4 纵向 DOCX，且各表能够相互勾稽。

详细报价是自下而上的预算或重建估算。没有财务凭证时，不得把它表述为实际发生成本；没有市场询价或权威费率时，单价证据等级通常不高于 C/D。

## 建模顺序

1. 读取建设要求、参考工程量清单、现有系统文档、代码和部署资料。
2. 建立“现有系统功能基线”，逐项写明已实现状态、证据、复用方式和计价处理。
3. 建立 WBS：系统 → 模块 → 功能项。功能项是可独立说明内容、验收和人员投入的最小计价单元。
4. 对每个功能项填写主要内容、建设属性、难度、阶段、验收标准、证据等级、总人日和人员人日分配。
5. 确定月综合费率、每人月有效人日、风险准备率、币种、税费和价格基准日。
6. 用 `scripts/generate_detailed_quotation.py` 校验、复算并生成成果。

不要直接把建设要求中的段落当作模块总价。需求、数据、研发、测试、部署、培训等容易被遗漏的工作必须落到具体功能项；已经实现且不发生改造的功能只进入现状基线，不重复计价。

## 输入结构

复制 `templates/detailed-quotation-input.json`，至少填写：

| 对象 | 必填字段 | 说明 |
|---|---|---|
| `meta` | `project_name`、`price_base_date`、`currency`、`tax_basis`、`monthly_rate_cny`、`person_month_days`、`risk_reserve_rate` | 定义报价口径 |
| `personnel[]` | `name`、`role`、`responsibility` | 人员姓名在本次输入中必须唯一 |
| `current_system_baseline[]` | `module`、`function`、`status`、`evidence`、`integration`、`pricing` | 区分复用、改造、新建和不计价 |
| `modules[]` | `id`、`name`、`purpose`、`integration`、`phase`、`items` | 模块必须说明用途和与现有架构的融合方式 |
| `items[]` | `id`、`name`、`description`、`build_type`、`difficulty`、`days`、`acceptance`、`person_days` | 最小计价单元 |
| `implementation_plan[]` | `phase`、`period`、`work`、`deliverables`、`acceptance_payment`、`payment_ratio` | 阶段和付款比例不能替代功能计价 |
| `exclusions[]` | 文本 | 明确硬件、数据、测评、驻场、维护等边界 |

人员名称、费率、项目路径、服务器地址和业务数据只能放在本次输入或成果中，不得硬编码进 Skill。

## 计算规则

采用十进制定点计算和“四舍五入到分”：

```text
人日单价 = ROUND(月综合费率 ÷ 每人月有效人日, 2)
功能项合价 = ROUND(功能项人日 × 人日单价, 2)
模块建设基价 = Σ 模块内功能项合价
项目建设基价 = Σ 模块建设基价
风险准备 = ROUND(项目建设基价 × 风险准备率, 2)
预算总价 = 项目建设基价 + 风险准备
```

风险准备调整金额而不是反推新增工时。若用户要求按不同角色费率计价，应扩展输入为角色费率表并逐人员计算，不得继续套用统一人日单价。

## 强制勾稽

脚本和人工复核都必须满足：

1. 每个功能项的 `person_days` 合计严格等于该功能项 `days`；
2. 模块内功能项人日合计等于模块—人员矩阵该模块合计；
3. 所有模块人日合计、所有人员人日合计和项目总人日相等；
4. 人员金额按每个功能项已取整合价和人日占比采用“整数分最大余数法”分摊，保证每人金额非负且合计严格相等；
5. 所有人员分摊建设基价合计严格等于项目建设基价；
6. 各模块风险准备按建设基价采用“整数分最大余数法”分配，金额非负且合计严格等于项目风险准备；
7. 个人工作量占比合计为 100%，阶段付款比例必须合计为 100%，各阶段付款金额合计必须等于预算总价。

这些校验用于保证表与表之间能对账，不代表输入工作量本身已经获得委托方确认。

## 成果结构

正式方案至少包含：

1. 编制说明：对象、范围、基准日、税费、费率、公式、证据和排除项；
2. 报价总览：人日、人月、建设基价、风险准备和预算总价；
3. 模块汇总：模块用途、融合方式、人日、基价、风险和合计；
4. 分部分项明细：每个功能的内容、用途、建设属性、难度、人日、单价、合价、人员分配和验收；
5. 现有系统基线：已实现能力、证据、融合方式和计价处理；
6. 人员职责与工作量：个人职责、人日、人月、占比和分摊基价；
7. 模块—人员矩阵：每个人在每个模块的投入；
8. 实施与付款计划：阶段、交付物、验收条件和付款比例；
9. 范围边界、假设、风险和待补资料。

Excel 使用紧凑列宽、冻结表头、筛选、金额格式和 A4 纵向打印设置。DOCX 使用 A4 纵向、窄页边距、紧凑字体和按模块拆表，避免把几十列强塞进一张不可读的宽表。

## 生成命令

基础成果不需要第三方库：

```bash
python3 scripts/generate_detailed_quotation.py input.json \
  --output-dir output \
  --prefix 项目报价 \
  --formats json,csv,md
```

生成完整 Excel 和 Word 成果：

```bash
python3 -m pip install -r requirements-docs.txt
python3 scripts/generate_detailed_quotation.py input.json \
  --output-dir output \
  --prefix 项目报价 \
  --formats all
```

生成后必须打开或解析 XLSX/DOCX，检查文件完整性、纸张方向、表格数量和关键金额；不能只以脚本退出码为验收证据。
